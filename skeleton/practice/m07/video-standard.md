# Средства просмотра видео и стандарт видео-багрепорта

Задача выбора: (1) в каком формате команда записывает видео ошибок для Issues на GitHub;
(2) каким проигрывателем удобнее разбирать такие видео при ревью.

Ограничение площадки: GitHub на бесплатном тарифе принимает видео .mp4, .mov, .webm размером до 10 МБ.

## 1. Записанное видео

В рамках исследования был записан видео-багрепорт длительностью 60–90 секунд. На видео демонстрируется ошибка в Django-проекте, связанная с выполнением workflow GitHub Actions, описанного в файле .github/workflows/django.yml. После запуска автоматической проверки проект не проходит этап build 3.7, в результате чего workflow завершается с ошибкой.

Во время записи показаны открытие репозитория на GitHub, переход в раздел Actions, выбор workflow Django, просмотр журнала выполнения и сообщение об ошибке. Также продемонстрирован фактический результат — неуспешное завершение проверки проекта с кодом ошибки.

Для записи использовалась программа OBS Studio, версия 33.0.3. Видео сохранено в формате MP4 с использованием кодека H.264, разрешением 1280×720 и частотой 30 кадров/с. Итоговый размер файла составляет 23,9 МБ, что соответствует ограничению GitHub в 10 МБ.

| Лицензия, реклама, телеметрия | 0,15 | 5 | 5 | 5 | 4 |

Выбран проигрыватель для ревью: VLC media player. 
Почему: VLC получил наибольшую взвешенную оценку — 4,55 балла. Он открывает видео в форматах MP4, MKV и WebM, поддерживает замедление воспроизведения до 0,25×, покадровую перемотку, сохранение отдельных кадров и повтор фрагмента видео. Программа распространяется бесплатно, не содержит рекламы и подходит для анализа видео-багрепортов в проекте.
VLC особенно удобен при проверке ошибки в workflow .github/workflows/django.yml, поскольку позволяет остановить видео на нужном сообщении об ошибке, увеличить область с текстом журнала и сохранить проблемный кадр в файл frame.png.

## 5. Стандарт видео-багрепорта команды

Правила, по которым все участники записывают видео к Issues (используются с модуля 9):

- Формат, кодек, разрешение, частота кадров: MP4, видеокодек H.264/AVC, разрешение 1280×720, частота 30 кадров/с. Такой формат выбран из-за хорошей совместимости с браузерами и небольшого размера файла.
- Настройки записи (программа, параметр качества): Для записи используется OBS Studio версии 33.0.3. Качество устанавливается на уровне CRF 28 либо с битрейтом около 1,5–2 Мбит/с. Если в кадре отображается мелкий текст из журнала GitHub Actions, перед записью необходимо увеличить масштаб страницы до 125–150%.
- Длительность и размер: Рекомендуемая длительность видео — от 30 до 90 секунд. Максимальный размер файла — 10 МБ, поскольку это ограничение GitHub для прикрепляемых видео. Желательно сохранять запас и ограничивать размер файла примерно 8–9 МБ.
- Что обязательно в кадре: окно проекта или репозитория GitHub; раздел Actions; название workflow — Django;журнал выполнения workflow из файла .github/workflows/django.yml; видимые действия мыши и пользователя; сообщение об ошибке; при необходимости — адресная строка браузера, версия проекта, открытая консоль и используемая ветка.
- Что обязательно в тексте Issue рядом с видео: TODO (шаги, ожидаемый и фактический результат, время в видео, где видна ошибка)
- Чего не должно быть в кадре: краткое описание ошибки; шаги для воспроизведения; ожидаемый результат; фактический результат; название workflow и файла .github/workflows/django.yml; версию приложения, ветку и окружение; временную отметку, на которой появляется ошибка, например 00:18; при необходимости — имя сохранённого кадра frame.png.
- Где хранить, если видео больше лимита: Сначала необходимо уменьшить разрешение, частоту кадров или качество видео и повторно экспортировать файл в MP4. Если размер всё равно превышает 10 МБ, видео следует разместить во внутреннем корпоративном хранилище или другом согласованном командой сервисе. В Issue добавляется ссылка на файл с доступом для всех участников проекта. Публиковать видео с конфиденциальными данными в открытом доступе запрещается.
